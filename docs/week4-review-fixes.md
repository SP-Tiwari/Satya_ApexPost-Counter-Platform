## How the contracts were republished

This machine has no User Secrets for the API, so the documents were first taken from the integration-test host (`ApiFactory("Development")`), which serves the same generator output. Only the `servers` URL was set back to the documented `https://localhost:7280/`.

Before the merge, the API was also started on Kestrel over HTTPS, with its settings (`ConnectionStrings__ApexPostDb`, the JWT signing key and a partner key) supplied as environment variables for that session only, against a disposable, migrated `ApexPost_Audit_*` database that was dropped afterwards. The `/openapi/v1.json` and `/openapi/v2.json` it served were identical to `contracts/v1.json` and `contracts/v2.json` apart from `servers`. Against the running API, the alias returned the same status codes as `/api/v1` for every operation with no token, a Courier token and an Admin token. The list returned 200 to a Courier in v1, v2 and the alias, and v2 `latestScan.scanType` was `"InTransit"`. The diff of both contracts shows only the intended changes: the list's 403 response in v1 and v2, and in v2 the `latestScan.scanType` reference and the new `LatestScanType` schema. `PublishedContractTests` passes against them. The client was regenerated with the pinned `NSwag.ConsoleCore` 14.7.1 (`dotnet tool restore`, then `dotnet nswag run src/ApexPost.Client/nswag.json`).
